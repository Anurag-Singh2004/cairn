01 / The Approach

Make the security claim face a test.

CAIRN compares a deliberately leaky positive control against a hardened isolation configuration. If the harness cannot catch planted leaks in the baseline, clean results cannot be trusted.

01

T0 · Leaky Baseline

A deliberately weak reference setup with flat networking and shared storage. Proves the test suite detects planted side channels and fault leakage.

Positive controlExpected leakage
02

T1 · Hardened Tier

Docker services execute with isolated bridge networks, non-root users (UID 10001), read-only root filesystems, dropped Linux capabilities, and quantized deadlines.

Network isolationLeast privilegeFail-closed
03

Cryptographic Proof

Audit events form an append-only SHA-256 hash chain anchored to Ed25519-signed checkpoints. Verifiers inspect Merkle paths offline without trusting the runner.

03 / Verifiable Cryptographic Evidence

Reviewers do not need to trust the runner.

Every finding emitted during benchmark execution is committed into an append-only hash chain and tied to an Ed25519-signed witness checkpoint.

✓
Ed25519 Signed Checkpoints Checkpoints commit to Merkle roots, run IDs, and tree sizes with cryptographic signatures.
✓
SHA-256 Append-Only Event Chain Events are strictly hash-linked; any retrofitted or modified event invalidates downstream hashes.
✓
RFC 6962 Merkle Inclusion Proofs Individual finding receipts provide compact logarithmic proofs to the signed root.
✓
Independent Offline Recomputation The verifier recomputes all invariants (I1–I9) without communicating with the runner or containers.
Verify Evidence Locally
make verify RUN=<run-id>

Or verify a specific finding receipt JSON directly:

python -m cairn.cli verify receipt_f_001.json

Tamper resistance: mutating even 1 byte in the ciphertext, signature, or Merkle path causes the verifier to reject the receipt immediately with exit code 1.

!

Scope, Assumptions, and Limitations

The benchmark runs demonstrated here use SimEngine, a deterministic simulated model backend designed to produce repeatable timing and cache distributions for security testing, not production LLM inference or real GPU hardware. “NO_SIGNAL_AT_POWER” denotes that no side-channel signal was detected within the specified sample sizes (N=200 for L1, N=29 for L3) and inspected locations; it does not constitute mathematical proof of universal side-channel immunity. Kernel-level vulnerabilities, physical CPU microarchitectural attacks, and referee private-key compromises are outside the stated threat model.
